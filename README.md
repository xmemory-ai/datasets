# Memory benchmarking datasets (xmemory)

This repository holds **memory benchmarking datasets** we used at **xmemory**. It is a **mixed bag**: cleaned-up exports, forked material, and semi-manually generated bundles sit side by side.

## Datasets

Each dataset lives in its **own top-level directory**. Some include **cooking or generation scripts** alongside the data.

### `extraction/` — Insurance claims structured extraction

- **Source.** Built on top of the insurance-claims subset of [Cleanlab's structured-output-benchmark](https://github.com/cleanlab/structured-output-benchmark), with further cleanup to drop incorrect and ambiguous labels. Credit to **Cleanlab** for the original dataset.
- **License.** Apache 2.0 (carried over from upstream).
- **What it tests.** Structured extraction from free-text insurance-claim documents into a four-area schema (basic claim, policy, list of insured objects, incident). The read pattern is a **single extraction pass per document**, scored at three increasing strictness levels: field-level precision/recall/F1, object-level accuracy, and output-level accuracy. The pipeline also reports retry rate and convergence of its local validation loop.
- **Motivation.** Most extraction benchmarks stop at field-level overlap. This dataset pushes evaluation to **object-level and output-level correctness** — the level a downstream system actually consumes — and treats validation-loop dynamics as a system-health signal. That combination is hard to find off the shelf.

### `end_to_end/` — Domain memory scenarios (corporate, education, finance, medical)

- **Source.** Generated in-house at xmemory across four domains: **corporate** (companies, employees, departments, projects), **education** (courses, students, instructors, assignments), **finance** (accounts, transactions, budgets, reports), and **medical** (patients, doctors, treatments, prescriptions).
- **License.** MIT.
- **What it tests.** Mixed **write/read workloads** against a memory system holding **typed entities and the relations between them**, one schema per domain. Reads cover single-fact lookups, aggregations over related entities, and questions whose answers depend on combining multiple prior writes. Each domain exercises a different relational shape and vocabulary, with answers scored by an LLM judge for precision/recall/F1 (judge prompt and synthesis prompt are documented in `end_to_end/README.md`).
- **Motivation.** Public memory benchmarks (e.g. LongMemEval, LoCoMo) are dominated by **chat-history Q&A over a single user**. They rarely probe a memory system's ability to maintain **typed, relational state** across a real domain, which is the workload most production memory deployments actually face. These four domains give us controllable, schema-aware scenarios that map onto realistic enterprise use.

### `splitwise/` — Friendly Expenses ledger

- **Source.** Generated in-house at xmemory. Scenario inspired by the Splitwise app for casual group expenses; internally called **Friendly Expenses**. Both the data and the generator code are shipped (under `code/`).
- **License.** MIT.
- **What it tests.** **Journaled writes** of group expenses (who paid, who participated, amounts) and **reads that require arithmetic over the full history** — balance-style "who owes whom how much" questions. Crucially, the correct answer cannot be retrieved from any single write; it requires **aggregating and netting** across the whole ledger.
- **Motivation.** It isolates a capability most public memory benchmarks ignore: **summation and reconciliation across many small, structurally similar facts**. Because the data is autogenerated, seeds, group sizes, and phrasings can be varied freely — useful for measuring overfitting and run-to-run inconsistency, and for keeping the benchmark fresh.

## Benchmark bundle layout

Every published bundle follows the same **three-level YAML layout**:

```text
<benchmark>.yml             # benchmark — metrics, thresholds, pointer to dataset
<benchmark>/                # dataset directory
  ├── dataset.yml           # dataset — scenario + instance setup (the schema)
  └── inputs/
      └── data.yml          # inputs — write/read actions with labels
```

In short, **benchmark → dataset → inputs**: a benchmark points at a dataset; the dataset's scenario and instance setup describe the schema; the inputs are the sequence of writes, reads, and evals against a memory system.

## Format

We publish datasets in our own **YAML shape**. The structure is small and self-evident from the files, so it is straightforward to consume with standard YAML tooling or AI-assisted coding.
